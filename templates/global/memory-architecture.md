# Архитектура Памяти

Этот файл описывает предпочтительную архитектуру памяти для совместной работы с агентом между проектами.

## Кратко

Используй слоистую модель памяти:

1. Глобальная память для всех проектов в `{{GLOBAL_MEMORY_DIR}}/`
2. Проектный стартовый слой и долговременная память в корне репозитория
3. Проектная хронологическая и тематическая рабочая память в `memory/`

## Глобальный Слой

Глобальный каталог памяти предназначен только для сведений, которые должны действовать между проектами.

- `{{GLOBAL_MEMORY_DIR}}/global-collaboration-rules.md` - правила сотрудничества для всех проектов
- `{{GLOBAL_MEMORY_DIR}}/memory-architecture.md` - общая структура памяти и соглашение об именах
- Стартовый файл в каталоге конфигурации агента — короткий указатель на эти канонические файлы; установщик поддерживает `{{CODEX_DIR}}/AGENTS.md` и `{{DSH_DIR}}/AGENTS.md`.
- `{{HOME_DIR}}/AGENTS.md` — необязательный индекс для работы внутри домашнего каталога; его наличие не гарантирует глобальную загрузку конкретным харнессом.

Не храни здесь проектную архитектуру или историю реализации конкретного проекта.

Для новой установки общий каталог по умолчанию — `~/.agents/memories`. Существующая установка в `~/.codex/memories` продолжает использоваться без переноса. Если существуют оба каталога, явно выбери один через `--global-memory-dir` / `-GlobalMemoryDir`. Не создавай отдельную копию общей памяти в `.dsh` и не выбирай источник по времени изменения файлов.

Стартовые файлы содержат ссылки, а не независимые копии правил. Обычная ссылка на Markdown-файл не означает автоматическую загрузку: агент должен прочитать указанные файлы и явно сообщить, если они недоступны. Политики среды и прямое задание пользователя имеют приоритет над файловой памятью.

## Форматы Путей

- В файлах памяти держи точные ссылки, нужные для проверок в используемых окружениях.
- Git Bash/MSYS и POSIX-проверки используют формат `/c/...`, например `{{GLOBAL_MEMORY_DIR_POSIX}}/global-collaboration-rules.md` и `{{GLOBAL_MEMORY_DIR_POSIX}}/memory-architecture.md`.
- Нативные Windows-оболочки и PowerShell используют формат `C:\...`, например `{{GLOBAL_MEMORY_DIR_WINDOWS}}\global-collaboration-rules.md` и `{{GLOBAL_MEMORY_DIR_WINDOWS}}\memory-architecture.md`.
- Когда открываешь файл shell-командой, выбирай формат активной оболочки, а не переписывай канонические ссылки ради другого окружения.

## Проектный Слой

Предпочтительное соглашение внутри проекта:

- `AGENTS.md` - локальный порядок старта и протокол памяти
- `START-HERE.md` - стартовый индекс
- `assistant-memory.md` - долговременные архитектурные решения и рабочие соглашения проекта
- `memory/current-work-queue.md` - текущая декомпозированная очередь реализации и рекомендуемые следующие шаги
- `memory/YYYY-MM-DD.md` - краткие хронологические заметки за день
- `memory/topic-<slug>.md` - повторяющиеся темы, причины решений и развивающиеся тематические заметки

## Правила

- Держи один канонический источник для каждого типа информации.
- Используй глобальные файлы только для долговременных правил между проектами.
- Используй `assistant-memory.md` для долговременных проектных правил и архитектуры, а не для ежедневных логов.
- Используй `memory/current-work-queue.md` для текущей очереди реализации, а не для долговременных архитектурных правил.
- Используй ежедневные файлы для коротких хронологических заметок.
- Используй тематические файлы для повторяющихся тем, более глубокого обоснования и развивающихся обсуждений дизайна.
- Предпочитай ссылки между слоями вместо копирования больших фрагментов текста.
- Держи имена и структуру одинаковыми между проектами, чтобы новая сессия могла предсказуемо ориентироваться в любом репозитории.

## Создание Каркаса

Чтобы создать файлы проектной памяти в новом репозитории, используй `init-project.sh` в POSIX/WSL или команду `init-project` в `memory-kit.ps1` на Windows.

Если пользователь просит "инициализируй проектную память" без указания пути к набору, считай это запросом на создание проектного слоя памяти в текущем рабочем каталоге через `codex-memory-kit`.

Расположение исходного набора фиксируется при установке независимо от каталога агента:

- Windows и PowerShell: `{{KIT_ROOT_WINDOWS}}`
- POSIX/WSL: `{{KIT_ROOT_POSIX}}`

Перед запуском проверь существование этого каталога. Если он найден, используй `scripts/memory-kit.ps1 init-project -Repo <текущий проект> -GlobalMemoryDir <общая память>` на Windows или `scripts/init-project.sh --repo <текущий проект> --global-memory-dir <общая память>` в POSIX/WSL. Передавай тот же каталог общей памяти, что указан выше. Если набор переместили, уточни его расположение. Путь клонирования не определяет место хранения памяти.

## Протоколы Для Конкретных Агентов

Секции ниже являются адаптерами под конкретных ИИ-агентов и их встроенную архитектуру памяти. Агент применяет только секцию, где он явно назван в заголовке. Секции для других агентов нужно игнорировать, а не переносить по аналогии: разные агенты могут иметь разные встроенные memory tools, checkpoint, history, scratchpad и правила записи.

Если для текущего агента нет отдельной секции, используй только общую файловую архитектуру выше: глобальные правила, `AGENTS.md`, `START-HERE.md`, `assistant-memory.md` и `memory/`.

### Протокол Для Codex (не для других агентов)

- Глобальная точка входа Codex — `{{CODEX_DIR}}/AGENTS.md`; непустой `AGENTS.override.md` в том же каталоге имеет приоритет. Если используется нестандартный `CODEX_HOME`, передай установщику соответствующий `--codex-dir` / `-CodexDir` и явный каталог общей памяти.
- Домашний `~/AGENTS.md` не заменяет эту глобальную точку входа. После настройки начни новую сессию и проверь, что загружен стартовый файл и прочитаны оба канонических файла.
- Если заявленный skill не читается по указанному `source locator`, не считай skill недоступным и не переходи на обходной путь, пока не проверишь актуальный файл в cache: `{{CODEX_DIR}}\plugins\cache\**\skills\<skill-name>\SKILL.md`. Если найден один актуальный путь — прочитай его; если найдено несколько версий — используй самую свежую версию плагина.
- Если при добавлении изменений, staging или commit в проектной папке возникают проблемы с `dubious ownership`, `index.lock`, правами на `.git` или доступом sandbox-пользователя к репозиторию, напоминай пользователю о настройке доступа и давай готовые команды для текущей оболочки, включая `git config --global --add safe.directory ...` и, для Windows/Git Bash, `MSYS_NO_PATHCONV=1 icacls ...`. Предлагай только права, необходимые для согласованного действия и реальной среды.
- Особенности sandbox, доступа к `.git` и разрешений относятся к текущей среде Codex. Не переноси настройки доступа на другие харнессы автоматически.

### Протокол Для DSH / DeepSeek Harness (не для других агентов)

- В стандартном профиле с `dsh-agent-instructions` глобальная цепочка начинается с `$DSH_HOME/AGENTS.md` (обычно `~/.dsh/AGENTS.md`), затем читает `$DSH_AGENTS_HOME/AGENTS.md` (обычно `~/.agents/AGENTS.md`). Далее загружаются проектные инструкции. Профиль может отключать этот плагин; поведение установленной версии нужно проверить в новой сессии.
- Установщик с `--agent dsh` / `-Agent dsh` создаёт `{{DSH_DIR}}/AGENTS.md` как короткий указатель на общую память `{{GLOBAL_MEMORY_DIR}}/`. Для нестандартного `DSH_HOME` передай `--dsh-dir` / `-DshDir`. Не складывай ещё одну копию правил в каталог DSH и не рассчитывай на глобальную загрузку `~/AGENTS.md`.
- Указатели не импортируют файлы автоматически, а прочитанный текст не становится системной инструкцией. Перед содержательной работой прочитай общие правила, эту архитектуру и проектный стартовый слой, если их актуального содержимого ещё нет в контексте. Если чтение недоступно, обозначь это ограничение.
- История сессий, compaction, todo и прочие доступные инструменты DSH — рабочий контекст. Канонические правила, решения и результаты сохраняются в общей или проектной файловой памяти по её протоколу; не редактируй внутреннее хранилище сессий ради синхронизации.
- Как внешний исполнитель соблюдай область задания, разрешённые пути, требуемый результат и критерий готовности. Не изменяй глобальные правила, настройки других агентов или чужую очередь задач без соответствующего разрешения. При передаче результата укажи изменения, фактические проверки и оставшиеся ограничения.
- Проверка загрузки: в новой сессии из целевого проекта перечисли реально загруженные стартовые файлы, прочитанные канонические файлы и действующие границы задания. Если несколько глобальных файлов противоречат друг другу, явно обозначь противоречие; не объявляй настройку подтверждённой только по наличию файлов.

Источники механизма загрузки (состояние upstream на 2026-10-20): [DSH agent instructions](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/context/agent-instructions/README.md), [Codex AGENTS.md](https://developers.openai.com/codex/guides/agents-md). Версия и состав локального профиля могут отличаться.

### Протокол Для MiMoCode (не для других агентов)

Эта секция описывает, как MiMoCode сочетает свою встроенную память с файловой памятью проекта выше.

#### Разделение Ответственности

| Встроенная память MiMoCode | Файловая память проекта |
|---|---|
| Автоматическая сериализация сессий (`checkpoint.md`) | Глобальные правила сотрудничества |
| BM25-поиск по memory scopes (`global`/`projects`/`sessions`) | Архитектура и соглашения проекта |
| Scratchpad (`notes.md`) | Стартовый протокол `AGENTS.md` -> `START-HERE.md` |
| Прогресс по задачам (`tasks/<id>/progress.md`) | Текущая очередь, хронологические и тематические заметки |

#### Порядок Доступа К Памяти

1. **Rebuild**: если checkpoint dump уже в контексте, не перечитывай его целиком; используй точечный поиск или чтение только по конкретным вопросам при truncation.
2. **Поиск по правилам и архитектуре**: используй `memory` tool (BM25) по scopes `global` и `projects` как быстрый индекс.
3. **Проверка по файлам проекта**: подтверждай важные факты чтением файловой памяти (`AGENTS.md`, `assistant-memory.md`, `memory/*.md`).
4. **Поиск по прошлым сессиям**: используй `history` tool, когда `memory` tool и файловая память не дали результата.

#### Запреты Для MiMoCode

- Не дублируй в `MEMORY.md` то, что уже есть в `assistant-memory.md`; используй ссылки и короткие указатели.
- Не создавай ad-hoc файлы памяти вне установленной структуры.
- При записи в `MEMORY.md` отмечай, является ли правило глобальным межпроектным или проектным.
- Не считай встроенную память MiMoCode заменой файловой памяти проекта; устойчивые правила и решения закрепляй в файловом источнике правды.

### Протокол Для ZCode (не для других агентов)

Эта секция описывает, как ZCode сочетает свою встроенную память с файловой памятью проекта выше. Общие правила разделения слоёв, единого источника истины и предпочтения ссылок действуют и здесь — ниже только то, что специфично для встроенной памяти ZCode.

Пути относятся к каталогу данных ZCode (по умолчанию `~/.zcode/`): `v2/` содержит индекс и логи, `cli/db/` — основное SQLite-хранилище.

#### Карта Встроенной Памяти

| Встроенная память ZCode | Роль в работе |
|---|---|
| Полная персистентная запись сессий (`cli/db/db.sqlite`: таблицы `session`, `message`, `part`) | Холодный источник сырых фактов диалога |
| Авто-компактизация при переполнении контекста (`session.time_compacting`, `session_entry` под summary/handoff) | Гарантирует, что `ReadSessionContext` безопасен даже для длинных сессий |
| Доступ к прошлым сессиям через `ReadSessionContext` (стратегии `relevant` / `handoff`) | Аналог встроенного `history` у других агентов |
| Индекс задач по workspace (`v2/tasks-index.sqlite`, ключ `workspace_key`) | Быстрый поиск релевантной сессии без перебора |
| Чекпойнты репозитория (`v2/repo-snapshots/<hash>/`) | Механизм отката состояния, не источник истины по решениям |

#### Порядок Доступа К Встроенной Памяти

1. **Контекстное окно сессии**: текущий диалог уже в памяти; не перечитывай его инструментами.
2. **Поиск по прошлым сессиям** — только когда файловая память проекта не дала ответа:
   - `relevant` — фокусный запрос по конкретному вопросу (дёшево, точечно);
   - `handoff` — возобновление прерванной задачи (даёт свёрнутый summary для продолжения).
3. **Индексация по workspace**: при поиске релевантной сессии ориентируйся на `tasks-index.sqlite` (индекс по `workspace_key`), а не на перебор всех сохранённых сессий.
4. **Откат состояния**: для восстановления репозитория используй `repo-snapshots/<hash>/` как холодный чекпойнт.

#### Запреты, Специфичные Для ZCode

- Не тяни прошлую сессию целиком, когда достаточно точечного запроса `ReadSessionContext` со стратегией `relevant`.
- Не применяй `handoff` для разового вопроса — она дороже и даёт избыточный контекст; используй её только для продолжения задачи.
- При подозрении на устаревший проектный контекст используй время последней сессии (`session.time_updated` в `db.sqlite`) как сигнал для сверки. Проверь содержимое и согласованные решения в относящихся к задаче файлах; одна дата изменения не определяет приоритет и не разрешает перезапись канонической памяти.

### Протокол Для Antigravity (не для других агентов)

Эта секция описывает, как Antigravity объединяет свои временные инструменты сессии с долгосрочной файловой памятью.

#### Карта Встроенной Памяти

| Встроенная память Antigravity | Роль в синергии с проектом |
|---|---|
| Артефакты (`task.md`, `implementation_plan.md`) | Локальная детализация и согласование задач, взятых из `memory/current-work-queue.md`. |
| Транскрипты сессий (`transcript.jsonl`) | Резервный лог действий для точечного поиска старых команд через `grep_search`. |
| Адаптер `.gemini/rules/antigravity-memory-adapter.md` | Стартовый указатель на общие правила и порядок согласования изменений памяти. |
| Глобальные правила (через `/learn`) | Если установленная версия поддерживает `/learn`, сохраняй там короткий указатель на канонические правила после согласования; это не гарантия соблюдения правил. |


#### Порядок Доступа К Памяти

1. **Управление задачами**: `memory/current-work-queue.md` — глобальный макро-бэклог. Встроенный `task.md` — микро-чеклист на текущую сессию. Бери задачу из бэклога, декомпозируй в `task.md`, по завершении обнови бэклог.
2. **Кристаллизация решений**: Устойчивые правила из временных артефактов (`implementation_plan.md`, `walkthrough.md`) по итогу сессии обязательно переноси в `assistant-memory.md` или `topic-<slug>.md`. Сами артефакты в репозиторий не идут.
3. **Поиск**: Используй инструмент `grep_search` по директории `memory/` для быстрого нахождения прошлых контекстов.
4. **Установка и обновление памяти**: При установке или развертывании набора памяти никогда не заменяй существующие файлы глобальной и домашней памяти флагом принудительной перезаписи (`-Force` / `--force`). Сначала изучи имеющиеся файлы, сравни с шаблонами (diff/merge), сохрани кастомные правила пользователя и запроси явное подтверждение перед замене.

#### Запреты Для Antigravity

- Не используй сессионные артефакты как замену долгосрочной памяти; они живут только в пределах сессии.
- Не читай длинные memory-файлы целиком без нужды, предпочитай `grep_search`.
- Не применяй принудительную перезапись (`-Force` / `--force`) при развертывании или обновлении глобального и домашнего слоев памяти поверх существующих файлов без предварительного чтения, разбора разницы (diff) и согласия пользователя.
- Не считай наличие файла или команды `/learn` доказательством загрузки либо соблюдения правил. Проверь доступный механизм правил в установленной версии; сохраняй ссылки на канонический источник и общий порядок согласования изменений памяти.
