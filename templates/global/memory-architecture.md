# Архитектура Памяти

Этот файл описывает предпочтительную архитектуру памяти для совместной работы с агентом между проектами.

## Кратко

Используй слоистую модель памяти:

1. Глобальная память для всех проектов в `{{GLOBAL_MEMORY_DIR}}/`
2. Проектный стартовый слой и долговременная память в корне репозитория
3. Проектная хронологическая и тематическая рабочая память в `memory/`

## Глобальный Слой

Глобальный каталог памяти предназначен только для сведений, которые должны действовать между проектами.

- `{{GLOBAL_MEMORY_DIR}}/global-collaboration-rules.md` - правила сотрудничества для всех проектов
- `{{GLOBAL_MEMORY_DIR}}/memory-architecture.md` - общая структура памяти и соглашение об именах
- `{{HOME_DIR}}/AGENTS.md` - необязательный глобальный стартовый индекс для работы внутри домашнего каталога

Не храни здесь проектную архитектуру или историю реализации конкретного проекта.

## Форматы Путей

- В файлах памяти держи точные ссылки, нужные для проверок в используемых окружениях.
- Git Bash/MSYS и POSIX-проверки используют формат `/c/...`, например `{{GLOBAL_MEMORY_DIR_POSIX}}/global-collaboration-rules.md` и `{{GLOBAL_MEMORY_DIR_POSIX}}/memory-architecture.md`.
- PowerShell и shell-команды Codex Desktop используют формат `C:\...`, например `{{GLOBAL_MEMORY_DIR_WINDOWS}}\global-collaboration-rules.md` и `{{GLOBAL_MEMORY_DIR_WINDOWS}}\memory-architecture.md`.
- Когда открываешь файл shell-командой, выбирай формат активной оболочки, а не переписывай канонические ссылки ради другого окружения.

## Проектный Слой

Предпочтительное соглашение внутри проекта:

- `AGENTS.md` - локальный порядок старта и протокол памяти
- `START-HERE.md` - стартовый индекс
- `assistant-memory.md` - долговременные архитектурные решения и рабочие соглашения проекта
- `memory/current-work-queue.md` - текущая декомпозированная очередь реализации и рекомендуемые следующие шаги
- `memory/YYYY-MM-DD.md` - краткие хронологические заметки за день
- `memory/topic-<slug>.md` - повторяющиеся темы, причины решений и развивающиеся тематические заметки

## Правила

- Держи один канонический источник для каждого типа информации.
- Используй глобальные файлы только для долговременных правил между проектами.
- Используй `assistant-memory.md` для долговременных проектных правил и архитектуры, а не для ежедневных логов.
- Используй `memory/current-work-queue.md` для текущей очереди реализации, а не для долговременных архитектурных правил.
- Используй ежедневные файлы для коротких хронологических заметок.
- Используй тематические файлы для повторяющихся тем, более глубокого обоснования и развивающихся обсуждений дизайна.
- Предпочитай ссылки между слоями вместо копирования больших фрагментов текста.
- Держи имена и структуру одинаковыми между проектами, чтобы новая сессия могла предсказуемо ориентироваться в любом репозитории.

## Создание Каркаса

Чтобы создать файлы проектной памяти в новом репозитории, используй `init-project.sh` в POSIX/WSL или команду `init-project` в `memory-kit.ps1` на Windows.

Если пользователь просит "инициализируй проектную память" без указания пути к набору, считай это запросом на создание проектного слоя памяти в текущем рабочем каталоге через `codex-memory-kit`.

Стандартное расположение набора:

- Windows и PowerShell: `{{CODEX_DIR_WINDOWS}}\codex-memory-kit`
- POSIX/WSL: `{{CODEX_DIR_POSIX}}/codex-memory-kit`

Перед запуском проверь, что каталог набора существует в стандартном месте. Если он найден, не спрашивай путь у пользователя: используй `scripts\memory-kit.ps1 init-project -Repo <текущий проектный каталог> -ProjectName <имя проекта>` на Windows или `scripts/init-project.sh --repo <текущий проектный каталог> --project-name <имя проекта>` в POSIX/WSL. Если стандартный каталог не найден, только тогда попроси пользователя уточнить расположение набора.

## Протоколы Для Конкретных Агентов

Секции ниже являются адаптерами под конкретных ИИ-агентов и их встроенную архитектуру памяти. Агент применяет только секцию, где он явно назван в заголовке. Секции для других агентов нужно игнорировать, а не переносить по аналогии: разные агенты могут иметь разные встроенные memory tools, checkpoint, history, scratchpad и правила записи.

Если для текущего агента нет отдельной секции, используй только общую файловую архитектуру выше: глобальные правила, `AGENTS.md`, `START-HERE.md`, `assistant-memory.md` и `memory/`.

### Протокол Для MiMoCode (не для других агентов)

Эта секция описывает, как MiMoCode сочетает свою встроенную память с файловой памятью проекта выше.

#### Разделение Ответственности

| Встроенная память MiMoCode | Файловая память проекта |
|---|---|
| Автоматическая сериализация сессий (`checkpoint.md`) | Глобальные правила сотрудничества |
| BM25-поиск по memory scopes (`global`/`projects`/`sessions`) | Архитектура и соглашения проекта |
| Scratchpad (`notes.md`) | Стартовый протокол `AGENTS.md` -> `START-HERE.md` |
| Прогресс по задачам (`tasks/<id>/progress.md`) | Текущая очередь, хронологические и тематические заметки |

#### Порядок Доступа К Памяти

1. **Rebuild**: если checkpoint dump уже в контексте, не перечитывай его целиком; используй точечный поиск или чтение только по конкретным вопросам при truncation.
2. **Поиск по правилам и архитектуре**: используй `memory` tool (BM25) по scopes `global` и `projects` как быстрый индекс.
3. **Проверка по файлам проекта**: подтверждай важные факты чтением файловой памяти (`AGENTS.md`, `assistant-memory.md`, `memory/*.md`).
4. **Поиск по прошлым сессиям**: используй `history` tool, когда `memory` tool и файловая память не дали результата.

#### Запреты Для MiMoCode

- Не дублируй в `MEMORY.md` то, что уже есть в `assistant-memory.md`; используй ссылки и короткие указатели.
- Не создавай ad-hoc файлы памяти вне установленной структуры.
- При записи в `MEMORY.md` отмечай, является ли правило глобальным межпроектным или проектным.
- Не считай встроенную память MiMoCode заменой файловой памяти проекта; устойчивые правила и решения закрепляй в файловом источнике правды.

### Протокол Для ZCode (не для других агентов)

Эта секция описывает, как ZCode сочетает свою встроенную память с файловой памятью проекта выше. Общие правила разделения слоёв, единого источника истины и предпочтения ссылок действуют и здесь — ниже только то, что специфично для встроенной памяти ZCode.

Пути относятся к каталогу данных ZCode (по умолчанию `~/.zcode/`): `v2/` содержит индекс и логи, `cli/db/` — основное SQLite-хранилище.

#### Карта Встроенной Памяти

| Встроенная память ZCode | Роль в работе |
|---|---|
| Полная персистентная запись сессий (`cli/db/db.sqlite`: таблицы `session`, `message`, `part`) | Холодный источник сырых фактов диалога |
| Авто-компактизация при переполнении контекста (`session.time_compacting`, `session_entry` под summary/handoff) | Гарантирует, что `ReadSessionContext` безопасен даже для длинных сессий |
| Доступ к прошлым сессиям через `ReadSessionContext` (стратегии `relevant` / `handoff`) | Аналог встроенного `history` у других агентов |
| Индекс задач по workspace (`v2/tasks-index.sqlite`, ключ `workspace_key`) | Быстрый поиск релевантной сессии без перебора |
| Чекпойнты репозитория (`v2/repo-snapshots/<hash>/`) | Механизм отката состояния, не источник истины по решениям |

#### Порядок Доступа К Встроенной Памяти

1. **Контекстное окно сессии**: текущий диалог уже в памяти; не перечитывай его инструментами.
2. **Поиск по прошлым сессиям** — только когда файловая память проекта не дала ответа:
   - `relevant` — фокусный запрос по конкретному вопросу (дёшево, точечно);
   - `handoff` — возобновление прерванной задачи (даёт свёрнутый summary для продолжения).
3. **Индексация по workspace**: при поиске релевантной сессии ориентируйся на `tasks-index.sqlite` (индекс по `workspace_key`), а не на перебор всех сохранённых сессий.
4. **Откат состояния**: для восстановления репозитория используй `repo-snapshots/<hash>/` как холодный чекпойнт.

#### Запреты, Специфичные Для ZCode

- Не тяни прошлую сессию целиком, когда достаточно точечного запроса `ReadSessionContext` со стратегией `relevant`.
- Не применяй `handoff` для разового вопроса — она дороже и даёт избыточный контекст; используй её только для продолжения задачи.
- После обновления файловой памяти проекта сверь таймстемп последней сессии (`session.time_updated` в `db.sqlite`) с временем правки соответствующего codex-файла. При расхождении приоритет у свежих данных `db.sqlite`; codex-файл нужно переписать.
