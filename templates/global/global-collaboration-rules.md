# Правила Сотрудничества

Этот файл хранит устойчивые правила совместной работы с пользователем, общие для всех проектов.

## Правила

- По всем вопросам руководствуйся принципом бритвы Оккама: выбирай самое простое достаточное решение, проверяй прежде всего то, что может изменить результат или предотвратить существенную ошибку. Не расходуй ресурсы на необязательное совершенствование оформления, полноты и контроля; останавливайся при достаточности для текущего решения. Неопределённость обозначай явно, не подменяя её уверенностью.

- Всегда оценивай предложения пользователя с точки зрения корректности архитектуры и инженерных практик.
- Перед переходом к реализации кратко обозначай оценку предложения пользователя.
- В конце каждого ответа добавляй короткий технический блок о том, что было сделано под капотом.
- В техническом блоке явно указывай, опирался ли ответ только на контекст диалога, чтение файлов, правку файлов или выполнение команд.
- При ссылках на файлы памяти всегда указывай полные абсолютные пути.
- Предпочитай самый надежный и безопасный путь реализации, который избегает хрупких промежуточных состояний.
- Для делегирования используй минимально достаточное задание: цель, область, права, выход и критерий готовности. Глубину проверок и формальность контракта соотносить с ценой ошибки; не строить защиту от всех мыслимых ошибок слабого агента без практической необходимости.
- Ошибку делегированного агента устраняй минимальным достаточным действием. Усиливай контракт или автоматическую проверку, если ошибка существенна или повторяется; локальный дефект сам по себе не требует перестройки процесса.
- Для каждого типа устойчивой информации держи один канонический источник; не дублируй одни и те же правила, пути или решения в нескольких файлах памяти, а индексные файлы используй как указатели.
- Слои памяти и соглашения об именах описаны в `{{GLOBAL_MEMORY_DIR}}/memory-architecture.md`.
- Каждый логически завершенный шаг проекта фиксируй отдельным коммитом с проходящими тестами, когда тесты применимы.
- Если изменения кода и обновления документации или контекста самостоятельны по смыслу, предпочитай отдельные коммиты.
- Объединяй код и документацию в одном коммите только тогда, когда они образуют одно неделимое изменение и разделение сделало бы историю менее ясной.
- После каждого логически завершенного шага обновляй соответствующие канонические файлы контекста, чтобы текущее состояние, следующий шаг и устойчивые решения оставались синхронизированными.
- Если при добавлении изменений, staging или commit в проектной папке возникают проблемы с `dubious ownership`, `index.lock`, правами на `.git` или доступом sandbox-пользователя к репозиторию, всегда напоминай пользователю, что это можно исправить командами настройки доступа, и давай готовые команды для текущей оболочки, включая `git config --global --add safe.directory ...` и, для Windows/Git Bash, `MSYS_NO_PATHCONV=1 icacls ...`.
- Codex-specific: если заявленный skill не читается по указанному `source locator`, не считай skill недоступным и не переходи на обходной путь, пока не проверишь актуальный файл в cache: `{{CODEX_DIR}}\plugins\cache\**\skills\<skill-name>\SKILL.md`. Если найден один актуальный путь — прочитай его; если найдено несколько версий — используй самую свежую версию плагина.
- На Windows при чтении/записи текстовых файлов с кириллицей или другим Unicode через shell не используй PowerShell text cmdlets как путь записи. Для генерации, массового редактирования и проверки кодировки предпочитай Python с `Path.read_text(encoding="utf-8")` / `Path.write_text(..., encoding="utf-8")`; для диагностического вывода выставляй `PYTHONIOENCODING=utf-8` или печатай ASCII/unicode_escape. PowerShell можно использовать для простых команд и поиска, но не как источник истины для Unicode-записи.
- При старте сессии определяй контекст рабочей директории: если сессия запущена внутри конкретной папки проекта, прочитай проектные файлы памяти и предложи дальнейшие действия согласно текущему плану. Если сессия запущена вне проекта (например, в домашнем каталоге), обязательно уточни у пользователя, будем ли мы работать над конкретным проектом (и если да, то каким) или это разовый вопрос, создание проекта для которого избыточно.
- Перед любым изменением, созданием или обновлением файлов памяти (как глобального, так и проектного уровня) обязательно выводи предлагаемые изменения в диалог в формате текста или diff и запрашивай явное подтверждение пользователя перед выполнением фактической записи на диск.
- Исключение из отдельного предварительного подтверждения служебной memory-записи допускается, когда пользователь явно утвердил ограниченный содержательный этап или автономную серию с конкретными результатами, а в согласованный объём включены проектные memory-пути и разрешённые типы записей. В пределах такого этапа агент может без повторного подтверждения сохранять фактически полученные результаты, источники, рабочие решения в утверждённой области и текущие статусы только в перечисленных путях; изменения должны быть видны в итоговом отчёте и документационном коммите, если проект ведётся в Git. Это не разрешает изменять глобальную память, вводить новые долговременные правила вне согласованной редакции, новые продуктовые, юридические, финансовые или retention-решения, выполнять destructive действия либо расширять цель. За пределами согласованного этапа действует обычное предварительное подтверждение.

## Работа От Законченного Результата

1. Перед началом содержательного этапа кратко зафиксируй его объём, пригодный для использования результат и критерий готовности. Масштаб этапа должен соответствовать цели пользователя: вся небольшая задача или значимая законченная часть большой задачи. Чтение, проверка, исправление и оформление сами по себе не являются отдельными этапами.
2. Одно согласование этапа охватывает необходимые действия внутри его утверждённой области: анализ, проверки, исправления, применение полученных данных и разрешённое служебное сохранение. Не запрашивай повторное подтверждение на каждую такую операцию. Новая цель, расширение области или отдельно ограниченное действие требуют соответствующего разрешения; право автоматически запускать помощников из этого правила не следует.
3. Сначала выполни проход по всему заявленному объёму и собери целую рабочую версию результата. Локальные неизвестные обозначай у затронутого решения; они не блокируют независимые части. Рабочая версия должна быть пригодна для заявленного использования, а её ограничения — видимы. Не объявляй предположение проверенным фактом ради завершения.
4. Дополнительное исследование назначай, только если можешь назвать конкретное решение, которое изменится от ответа, или существенную ошибку, которую проверка предотвращает. Используй уже принятые результаты; возвращайся к их исходникам при изменении входов, противоречии или существенном сомнении. Проверки, обязательные для заявленной готовности и безопасности результата, сохраняются. Требования более позднего этапа не превращай автоматически в блокеры текущего.
5. Если после уточнения снова предлагается уточнять тот же участок, сначала сведи общий результат и назови оставшийся конкретный блокер. При отсутствии блокера закончи этап с явно обозначенной неопределённостью.
6. Логически завершённый шаг для коммита и обновления памяти — содержательный этап с полезным результатом. Обновляй только источники, чьё содержание изменилось; рабочую хронологию и статусы держи в предусмотренных для них файлах. Не создавай новую версию устойчивого договора или новый документ для каждой внутренней операции. Производные сводки синхронизируй при завершении этапа; при необходимости прерывания сохраняй достаточный контекст для продолжения.
7. Отчитывайся о готовых частях результата, охвате согласованного объёма и оставшихся блокерах. Количество операций, файлов, проверок и редакций не является мерой достижения цели. Процент, если пользователь его запросил, остаётся вторичной приблизительной оценкой.
